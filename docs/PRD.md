# 个人记账系统 · 需求文档（PRD）

> 状态：初稿，待技术栈与去重口径确认
> 更新：2026-11-07

## 1. 背景与目标

用户有多渠道消费记录：微信、支付宝、信用卡。此前每条渠道账单单独统计，**跨渠道会产生重复记录**（例如：微信支付但资金来源是信用卡 → 微信账单和信用卡账单都出现这笔 → 月度收支被重复计算）。

目标：导入各渠道 Excel 账单 → 自动识别并合并跨渠道重复 → 准确给出**每个自然月**的实际收入 / 支出 / 净额。

## 2. 核心假设与边界（已烤问确认）

| 决策点 | 结论 | 影响 |
|---|---|---|
| 核算模型 | **C：只看月度净额** | 不建账户实体、不做余额、不做流水勾稽，系统大幅简化 |
| 自己账户间转账 | **默认过滤**（微信↔支付宝、信用卡还款） | 不计入收支 |
| 数据格式 | **Excel**，每月手动导出 | 不做自动登录导出网页版 |
| 部署 | 阿里云 2核2G Linux3，轻量 | Python 全栈单进程 |
| 开发顺序 | **先本地 Windows 跑通 → 再部署** | MVP 即可跑通全流程，扩展后置 |

### 2.1 统计口径定义（务必先对齐，否则数字对不上）

- **支出**：当月所有"消费类"交易的净支出（消费 − 退款）之和，**已合并的重复记录只算一次**。
- **收入**：当月"收入类"交易（工资、红包、退款退回等）。
- **净额 = 收入 − 支出**。
- **交易类型分类**：消费 / 收入 / 转账 / 退款 / 手续费 / 其他。仅"消费"与"收入"参与净额；"转账"过滤；"退款"冲减当月对应消费；"手续费"计入支出。
- **归属日期**：以**交易日**聚合（非信用卡入账日）。信用卡的入账日可能比消费日晚且跨月，若按入账日会把消费错误归到还款月。

## 3. 数据模型

### 3.1 实体

- `bill_file`：导入的账单文件（id, source, file_name, file_hash=sha256, imported_at, row_count）
- `transaction`：单笔流水（id, source, bill_type, amount, currency, tx_date, entry_date, merchant, counterparty, description, file_id, source_row, merged_group_id, confidence)
- `merge_group`：去重合并组（id, representative_tx_id, merged_count, auto_merged)
- `dedup_candidate`：待人工确认的疑似重复对（id, tx_a_id, tx_b_id, score, reason, status=pending/merged/discarded)

> C 模型下不建 `account` / `balance` 表。若未来改 B 模型，需追加账户实体与勾稽表。

### 3.2 字段说明要点

- `source`：wechat / alipay / card（可扩展）
- `amount`：正负号规范化——微信/支付宝支出常为负数，信用卡支出为正数，导入时统一：消费记正、退款记负。
- `confidence`：high / medium / low。
- `merged_group_id`：被合并的从记录指向同组代表记录。

## 4. 去重算法（系统灵魂）

### 4.1 两级去重

1. **同文件内去重**：同一账单文件里重复行（如微信账单导出的合并单元格导致多行相同）→ 直接删，置信 high。
2. **跨渠道去重**：任意两笔不同 source 的交易，判为疑似重复的条件：
   - |金额| 相等（容差 0.01，信用卡有手续费时允许微小差异）
   - |交易日间隔| ≤ 3 天
   - 商户名模糊匹配：一方 `merchant/counterparty` 的关键词包含出现在另一方 `description` 中；或去空格/大小写归一后匹配
   → 生成去重得分，按总分分档。

### 4.2 置信度分档动作

- **high**（金额 + 日期 + 商户名全中）：`auto_merged=true`，直接并入组，用户无需确认。
- **medium**（金额 + 日期命中，商户名对不上 / 仅一方匹配）：进 `dedup_candidate` 待确认队列，用户在 UI 一键 `merged`/`discarded`。
- **low**（仅金额命中或仅日期命中）：不自动合并，保留各自记录，可在报表层提示"疑似重复，请核对"。

### 4.3 关键现实坑（必须在文档显式声明，避免数字错）

- **商户名不匹配是头号失败原因**：信用卡账单商户常为 MCC/英文缩写，对面是中文名 → 必然落入 medium，需人工确认。**这是 C 模型的代价，已知接受**。
- **信用卡入账日 vs 交易日错位**：按交易日聚合；信用卡交易日从账单取。
- **退款跨月**：当月消费下月退款 → 退款记入退款所在月，净额跨月波动属正常口径。
- **分期手续费**：信用卡账单的分期手续费是真实支出，计入月度支出。
- **积分抵扣 / 红包**：需在账单里识别为"非真实消费"，过滤或作为收入抵减（视渠道）。
- **自我转账**：微信→支付宝、信用卡还款 → 过滤。
- **重复导入**：按 `file_hash` 防重，同一文件二次导入直接跳过。
- **负值 / 冲正**：部分渠道退款以负金额出现，导入时按 `bill_type=退款` 规范化。

## 5. 导入流程

1. 用户导出微信 / 支付宝 / 信用卡 Excel。
2. 上传（拖拽或选文件）→ 后端识别 source 与列映射（每种渠道一套列映射模板，首次需校准，存模板缓存）。
3. 解析为 transaction 落库。
4. 触发去重引擎：同文件内去重 → 跨渠道去重 → 生成 merge_group + dedup_candidate。
5. 报表按月度净额更新。

> 列映射模板会因渠道版本变化，需支持"首张表自动探测 + 手动校准列映射"。

## 6. 功能模块

### 6.1 MVP（核心，先做）

- 账单上传（三种渠道 Excel）+ 列映射自动探测
- 去重引擎 + 置信度分档 + 待确认队列
- 月度报表：收入 / 支出 / 净额
- 交易明细列表（可按 source / 月 / 类型筛选，能看到 merge_group 归属）
- 待确认去重队列的合并 / 解除操作
- 本地 Windows 一键跑通（依赖安装 + 启动脚本）

### 6.2 扩展（核心跑通后再做，明确后置）

- 分类报表（餐饮 / 交通 / 购物…）
- 预算提醒
- 可视化仪表盘（月度趋势、渠道占比）
- 多币种 / 外币卡折算
- 家庭成员共享
- 定时自动拉取账单

## 7. 非功能

- 轻量：单进程、SQLite、内存占用 < 300MB。
- 安全：账单文件不落明文长期存（导入后仅存结构化流水）；上传接口做基础校验。
- 可运维：Alembic 迁移、结构化日志、Docker 部署。
- 可移植：本地 SQLite，部署环境切换只需换 DB URL（代码层预留）。

## 8. 明确不做（Out of Scope）

- 账户余额管理、净资产核算（C 模型不需要）
- 网页版账单自动登录抓取
- 多人协作
- 发票 OCR

## 9. 风险

| 风险 | 应对 |
|---|---|
| 去重准确率不足（卡名不匹配） | 置信度 + 人工确认队列兜底；可在扩展期引入商户名别名表 |
| 渠道 Excel 版本变化导致列错位 | 列映射模板缓存 + 手动校准 UI |
| 信用卡入账日差异导致跨月归属错 | 强制按交易日聚合，入账日仅存储不聚合 |
| 2G 内存跑不动 | Python 全栈 + SQLite 单进程在这样的规格完全够 |

## 10. 决策定稿（2026-11-07）

| 决策点 | 结论 |
|---|---|
| 核算模型 | C：只看月度净额（不建账户/余额/勾稽） |
| 自己账户间转账 | 默认过滤 |
| 数据格式 | Excel，每月手动导出 |
| 前端方案 | **Jinja2 服务端渲染 + 原生 JS + Chart.js**（不上 Vue/React） |
| 去重口径 | **接受部分人工确认**：高置信自动合并，中置信待确认人工点，低置信保留 |
| 部署 | 阿里云 2核2G Linux3，轻量单进程 |
| 开发顺序 | 先本地 Windows 跑通 → 再部署 |

### 10.1 技术栈定稿

- 后端：Python 3.11 + FastAPI
- 数据库：SQLite + SQLAlchemy 2.0 + Alembic（代码层预留 Postgres 切换口）
- Excel：pandas + openpyxl
- 前端：Jinja2 + 原生 JS + Chart.js
- 部署：Docker 单容器（uvicorn）或 systemd

> 残留已知风险见 4.3（卡名不匹配、入账日错位、渠道版本变化），均为已知接受、非阻塞。
